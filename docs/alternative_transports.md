# Альтернативные транспорты: заготовка на будущее

Статус: **не внедрено, тестирование отложено.** 25.08.2026 выяснилось, что
жалоба «сервер пингуется, сайты не грузятся» была вызвана не транспортом, а
багом двойной выдачи `client_uuid` (см. `find_double_uuid_victims.py`), поэтому
менять gRPC на что-то другое прямо сейчас незачем. Заметка нужна, чтобы при
следующей волне блокировок не собирать всё это заново.

## Что известно про gRPC на август 2026

- Официальная документация Xray-core называет **XHTTP развитием gRPC** и
  отмечает, что gRPC-сервис предсказуемо отзывается на посторонние пробные
  обращения.
- Публикации 2026 года (Хабр, обсуждения в Xray-core) описывают переход
  операторского оборудования от разбора сигнатур к разбору **поведения**:
  учитывается подсеть сервера, отпечаток клиента и число одновременных
  TLS-соединений к одному адресу. Симптом — «подключение установлено, трафика
  нет», сброс на ~120 секунд.
- Reality закрывает только рукопожатие. Поведение потока после установки
  соединения он не меняет — это и есть слабое место.

Выводы отражены на странице `/status` (`website/status_data.json`, запись в
changelog от 25.08.2026).

## Как поднимались тестовые инбаунды

Важное: в конфиге Xray включён `HandlerService`, поэтому инбаунды **добавляются
на живом сервере без рестарта и без правки `config.json`**:

```bash
xray api adi  --server=127.0.0.1:62789 inbound.json   # добавить
xray api lsi  --server=127.0.0.1:62789                # посмотреть
xray api rmi  --server=127.0.0.1:62789 <tag> [<tag>…] # снять
```

Скрипт-генератор и end-to-end проверка лежали в скретчпаде сессии; логика
простая: взять `privateKey`/`shortIds` из живого конфига (чтобы `pbk` у клиента
не менялся), собрать инбаунд, добавить туда тестовый uuid, собрать `vless://`.

## Матрица, которая была собрана и проверена

Все пять поднимались на NL-ноде (193.233.127.32) и **проверены end-to-end**:
локальный xray-клиент по ссылке + `curl https://www.google.com/generate_204`
через socks → HTTP 204 на всех пяти.

| Порт | Транспорт | SNI | Что проверяет |
|------|-----------|-----|---------------|
| 8443 | XHTTP `stream-one` | свой (`www.horizance.ru`) | замена gRPC при прочих равных |
| 2053 | RAW/TCP + Vision | свой | режется ли именно gRPC |
| 2083 | XHTTP `stream-one` | чужой (`www.samsung.com`) | транспорт + чужой SNI |
| 2087 | RAW/TCP + Vision | чужой | изолирует фактор SNI |
| 2096 | XHTTP `packet-up` | чужой | максимально «браузерное» поведение |

Полезные пары для сравнения: **2083 vs 2087** — один SNI, разный транспорт;
**2053 vs 2087** — один транспорт, разный SNI.

Оговорка по методике: порты нештатные, а к 443 отношение у операторов другое,
поэтому положительный результат на 8443 сам по себе не доказывает превосходство
транспорта. Чисто сравнить можно только разнеся варианты по разным серверам,
каждый на 443.

Кандидаты для чужого SNI, проверенные на TLS 1.3 + h2 с нашей ноды:
`www.samsung.com`, `www.icloud.com`, `cdn.jsdelivr.net`, `www.tesla.com`,
`dl.google.com`. Не подошёл `swcdn.apple.com`.

## Про смену SNI — важное ограничение

Reality проксирует чужое рукопожатие на реальный `dest`, но **IP остаётся наш**.
Для стороннего SNI (`www.samsung.com`) картина «SNI самсунговский, адрес — нет»
внутренне противоречива, и это отдельный признак, а не маскировка. Текущая
схема — свой домен, который действительно живёт на этом же адресе и отдаёт
настоящий сайт, — по связке «домен ↔ адрес» непротиворечива. Менять SNI на
чужой имеет смысл только вместе с уходом за CDN, где наш адрес перестаёт быть
виден.

## Если понадобится вернуться

1. Поднять инбаунды по матрице выше (`adi`), зарегистрировать в них uuid
   тестового пользователя (`adu`).
2. Дать пользователю 2–3 ссылки, не больше, и обязательно вместе с рабочей
   штатной — иначе не с чем сравнивать.
3. Снять инбаунды через `rmi`, когда закончите: они не переживают рестарт Xray,
   но до него висят и слушают порты.
