## 1. Уйти с транспорта gRPC на XHTTP

**Приоритет:** средний. Сейчас всё работает, гореть не начало.

**Что менять:** `streamSettings.network` в конфиге Xray на всех нодах и
строку в `website/routers/vpn.py::get_settings_link`
(`type=grpc&serviceName=grpc_service` → `type=xhttp&path=...&mode=stream-one`).

**Почему:**

1. **Само ядро объявило gRPC устаревшим.** Xray 26.3.27 пишет это при каждом
   старте, дословно:
   `The feature gRPC transport (with unnecessary costs, etc.) is deprecated,
   not recommended for using and might be removed. Please migrate to XHTTP
   stream-up H2 as soon as possible.`
   То есть однажды транспорт просто выпилят из ядра, и обновление Xray сломает
   всех клиентов разом. Это главный аргумент — он про поддержку, а не про
   блокировки.
2. Официальная документация Xray называет XHTTP развитием gRPC и отмечает, что
   gRPC-сервис предсказуемо отзывается на посторонние пробные обращения.
3. gRPC добавляет накладные расходы поверх HTTP/2 по сравнению с RAW.

**Чем рискуем:** старые версии Happ могут не знать XHTTP. Перед переездом надо
проверить минимальную версию клиента у активных пользователей — она видна в
`User-Agent` в логах (`Happ/3.26.3/Android`, `Happ/5.6.0/ios` и т.д.).

**Сделано 25.08.2026:** XHTTP-инбаунд `vless_xhttp` поднят рядом с боевым gRPC
на порту 8443 через `xray api adi` (без рестарта, боевой инбаунд на 443 не
тронут). Пользователям НЕ раздаётся. Проверен сквозным трафиком:

    NL  OK 204     US  OK 204     RU  OK 204
    DE  OK 204     KZ  OK 204     MX  порт закрыт провайдером

Параметры: `mode=stream-one`, `path=/api/v3/messages`, reality-ключи и dest
взяты с боевого инбаунда каждой ноды (pbk у клиента не меняется). Ссылка для
проверки собирается так:

    vless://<uuid>@<host>:8443?security=reality&encryption=none&type=xhttp
      &path=%2Fapi%2Fv3%2Fmessages&mode=stream-one
      &sni=<credentials.SNI>&fp=chrome&pbk=<pbk>&sid=<shortId>

**Внесено в config.json на NL 25.08.2026** (бэкап
`/usr/local/etc/xray/config.json.bak_before_xhttp`, `xray run -test` →
`Configuration OK`). Сервис НЕ перезапускался: сейчас инбаунд работает из `adi`,
а после ближайшего рестарта поднимется уже из конфига. На остальных нодах — пока
только через `adi`.

**Два ограничения:**
1. Инбаунды из `adi` **не переживают рестарт xray**. Чтобы закрепить — вносить
   в `config.json`, а это рестарт + `restore_users.py`.
2. У MX открыты только 80/443/22 на уровне провайдера (не iptables). Там XHTTP
   можно поставить только на 443, то есть вместо gRPC, а не рядом.

Снять отовсюду: `xray api rmi --server=127.0.0.1:62789 vless_xhttp`

**Как делать:** не рубить gRPC сразу. Поднять XHTTP вторым инбаундом на
отдельном порту (`xray api adi`, без рестарта — см.
`docs/alternative_transports.md`), выдать в подписке ОБА варианта, дать неделю,
посмотреть по `access.log`, кто куда ходит, и только потом убирать gRPC.

## 2. Мексиканская нода — РЕШЕНО 25.08.2026

Оставлено для истории, чтобы не искать заново.

**Симптом:** через MX туннель не поднимался, клиент писал
`x509: certificate is valid for horizance.com, www.horizance.com, not
www.horizance.ru`. Сайт `horizance.com` при этом работал.

**Причина — НЕ сертификаты и НЕ dest.** Конфигурация MX верна по сути:
на этой машине крутится сайт `horizance.com`, поэтому `dest = 127.0.0.1:8080`
и `xver = 1` — так и должно быть (на NL то же самое, только там `horizance.ru`).

Дело в версии nginx. REALITY заимствует у `dest` рукопожатие **TLS 1.3** —
на TLS 1.2 она не работает вовсе. Замер с PROXY-заголовком, как это делает
сам xray:

    NL  (nginx 1.24.0): 127.0.0.1:8080 -> TLSv1.3   работает
    MX  (nginx 1.18.0): 127.0.0.1:8080 -> TLSv1.2   не работает

`ssl_protocols` не был задан явно ни там, ни там, а **в nginx 1.18 TLS 1.3
не входит в набор по умолчанию** (добавили только в 1.23.4). Пока nginx на MX
слушал 443 напрямую, в конфиге стояла явная строка `ssl_protocols TLSv1.2
TLSv1.3;` — при переносе на 8080 (24.08.2026, 20:40) её потеряли.

**Исправление:** вернули строку в server-блок 8080 и сделали
`systemctl reload nginx`. Бэкап — `/etc/nginx/nginx.conf.bak_before_tls13`.
Xray не перезапускался, клиенты не терялись, сайт не мигал.

**Отдельно, важно на будущее:** `dest` работает ещё и фолбэком для
постороннего трафика. Менять его на MX нельзя — сайт `horizance.com` сразу
ложится с ошибкой Cloudflare 526 (проверено на себе 25.08.2026).

**Ещё:** у MX закрыт весь входящий трафик кроме 80/443/22 на уровне
провайдера, а не iptables. Поднять тестовый инбаунд на другом порту там
нельзя — правило в iptables ничего не меняет.

## 3. Атрибуция: понимать, с какой страницы пришёл пользователь

**Приоритет:** низкий, это аналитика, а не поломка.

**Сейчас:** во всех ссылках на бота на сайте стоит `?start=183640993`. Это даёт
ровно один бит: «пришёл с сайта» против «пришёл сам». С какой страницы — не
видно, потому что метка одна на все страницы.

**Что даст доработка:** связку «поисковый запрос → страница входа → покупка».
Сейчас такую цепочку не построить: между визитом на сайт и Telegram-аккаунтом
нет общего идентификатора.

**Как это сделать (механика):**

1. Сайт на каждый показ страницы кладёт в свою сессию источник (страницу,
   реферер, utm) и генерирует разовый короткий токен.
2. Ссылка на бота рендерится как `?start=<токен>`. Шаблон `base.html` при этом
   ничего не знает про страницу — токен приходит в него переменной из
   контекста, который формирует обработчик страницы. Это обычная передача
   переменной в шаблон, а не магия: `base.html` просто печатает то, что дали.
3. Бот в `/start` отдаёт токен обратно на сайт (или лезет в общую таблицу) и
   получает источник.

**Что мешает прямо сейчас:** `bot.py:108`,
`referrer_id = int(event.message.text.split()[-1])`. Любой нечисловой payload
роняет `/start` целиком. Значит вместе с токенами надо переписать разбор
payload: отделить числовые id (реферальная программа) от текстовых меток.

**Осторожно:** `referrer_id` сейчас одновременно и «источник», и реферальная
программа. Нельзя брать «свободный» Telegram-id под метку: например
`6590559199` — это UserBot владельца, и по нему уже числятся два приглашённых
живых пользователя (`379549357`, `922145873`). Перезапись затрёт настоящие
данные.

## 4. MemorySession для основного бота — НЕ делать

**Решение: оставить `main.py` на файле сессии.** Пункт записан, чтобы к нему не
возвращаться.

Для разовых скриптов (`notify_by_condition.py`, `compensate_uuid_victims.py`)
`MemorySession` — правильный выбор: бот авторизуется токеном за доли секунды,
файл не нужен, и не возникает конкуренции за один sqlite с работающим
`main.py` (та самая `database is locked`).

Для постоянно работающего бота файл сессии полезен другим: в нём хранится
**состояние апдейтов** (`pts`/`qts`). После рестарта Telegram по этому
состоянию доотдаёт события, которые произошли, пока бот лежал. С
`MemorySession` состояние теряется, и сообщения за время простоя бот просто не
увидит. Поэтому у `main.py` файл сессии остаётся.

## 5. Мелочи, замеченные попутно

- `_run_ssh` ставит `timeout=25` и кладёт исключение в `str(e)`. У
  `TimeoutError` пустой `str()`, поэтому таймаут выглядит в логах как
  `{'success': False, 'error': ''}` — неотличимо от «непонятно что».
  **ИСПРАВЛЕНО 25.08.2026:** логируется тип исключения.
- **`VPNManager._get_config_settings` держится на позициях в конфиге:**
  `config['inbounds'][0]['tag']` и `config['inbounds'][1]['port']`. Любой новый
  инбаунд, вставленный не в конец, ломает боту api-порт. Напоролся 25.08.2026,
  добавляя XHTTP: бот стал считать api-портом 8443. Порядок в
  `/usr/local/etc/xray/config.json` обязан быть `vless_tls`, `api`, дальше что
  угодно. Правильнее — искать по `tag`, а не по индексу.
- `db.py::get_not_inactive_users_with_uuid(table)` принимает имя таблицы, но
  работает только с `users`: в `trial_sessions` нет колонки `status`. В проекте
  его так и зовут — только с `users` (`bot.py:328`), так что это не живой баг,
  а ловушка на будущее для того, кто поверит сигнатуре.

## 6. Автовосстановление клиентов после перезагрузки ноды

**Приоритет: высокий.** Сейчас о падении ноды узнаём от клиентов — это худший
из возможных источников.

**Главное: пинг тут не поможет.** После перезагрузки сервер прекрасно
пингуется, порт 443 открыт, xray запущен — а клиентов в памяти нет, потому что
они добавляются на лету через `xray api adu` и в `config.json` не пишутся.
Снаружи такая нода выглядит живой. Именно поэтому Happ показывает «сервер
доступен», а трафик не идёт.

Обратной связи от Happ не существует и не появится: приложение не имеет канала
для отчётов на наш сервер. Но она и не нужна — **NL-нода может опросить
остальные сама**, SSH-доступ ко всем шести у неё уже есть.

**Правильный признак — расхождение числа клиентов, а не доступность.**

    ожидаем = не-inactive юзеры с uuid + живые trial-сессии (из users.db)
    факт    = xray api inbounduser --tag=vless_tls | подсчёт email

Три исхода:

| Что видим | Что это | Действие |
|---|---|---|
| SSH не отвечает | нода реально лежит | письмо, восстанавливать нечего |
| SSH ок, клиентов сильно меньше ожидаемого (обычно 0) | xray перезапустился | `restore_users.restore_vpn(server)` + письмо |
| счётчики сходятся | всё хорошо | ничего |

**Куда встроить:** отдельный цикл в `utils.py` рядом с `start_timer`, но чаще —
раз в 10–15 минут (12 часов тут слишком долго). Использовать уже готовые
`VPNManager._run_ssh` и `restore_users.restore_vpn(server)`, письмо — через
`error_alerts.notify` с ключом на сутки, чтобы не заспамить.

**Осторожно:** восстановление должно быть идемпотентным. Оно уже такое —
`_register_clients` делает `rmu` перед `adu` (см. п.5), так что повторный
прогон ничего не ломает.

**Альтернатива, которая убирает проблему целиком:** писать клиентов не только в
память, но и в `config.json` каждой ноды. Тогда после перезагрузки xray
поднимется уже с клиентами и восстанавливать будет нечего. Цена — перезапись
конфига на каждое изменение подписки и риск разъезда файла с реальностью.
Мониторинг+восстановление проще и безопаснее, но этот вариант стоит держать в
уме, если падения станут частыми.

**Ещё:** проверить, что у systemd-юнита xray на всех нодах стоит
`Restart=always` — тогда падение самого процесса (не всей машины) лечится без
нас, но клиентов всё равно придётся восстанавливать.
